TCP切断を
図で触って理解する

TCPは接続を作るときだけでなく、終わらせるときにも状態を確認します。ここではクライアント側から正常終了する代表例を使い、FIN・ACK・TIME_WAITを順番に追います。

FIN → ACK → FIN → ACK を追う

開始時点では両方ESTABLISHEDです。「次へ」または「自動で見る」で、接続がCLOSEDになるまで進めます。

TCP接続の終了開始前
データ通信は終わりました。クライアントから接続終了を始めます。
クライアント終了を開始する側192.168.1.10:53024
ESTABLISHED
サーバー終了を受ける側203.0.113.10:443
ESTABLISHED

4回のやり取り

1. FINクライアントが「こちらから送るデータはもうない」と通知します。
2. ACKサーバーがFINを受け取ったことを確認します。この時点ではサーバー側からの送信はまだ可能です。
3. FINサーバー側のアプリも送信を終えると、サーバーからFINを送ります。
4. ACKクライアントがサーバーのFINを確認し、サーバー側はCLOSEDになります。

途中の状態には意味がある

FIN_WAIT_1 / FIN_WAIT_2先に終了を始めた側が、相手のACKやFINを待っている状態です。active closer
CLOSE_WAIT相手のFINは受信済み。ただし自分側のアプリがまだcloseしておらず、FINを返していない状態です。application close待ち
LAST_ACK自分のFINを送信し、最後のACKが返ってくるのを待っている状態です。final ACK待ち

TIME_WAITはなぜ残る？

最後のACKを送った側は、すぐに完全消滅せずTIME_WAITに入ります。主な目的は、最後のACKが失われて相手からFINが再送された場合にもう一度ACKを返せるようにすることと、古いTCPセグメントがネットワーク上から十分消える時間を確保することです。

TIME_WAITが見えること自体は異常ではありません。大量に残って問題になる場合は、接続の作り方やサーバー構成などを含めて原因を調べます。

FINは「双方向を一気に切る」ではない

FIN = 片方向の送信終了FINを送った側は「自分からはもう送らない」と伝えます。相手側から残りのデータを受信することはできます。これがTCPの半閉塞（half-close）につながります。
RST = 強制的な終了正常終了のFINとは別に、接続を即座にリセットするRSTがあります。RSTは通常のFIN/ACK終了とは意味が異なります。

接続開始と並べると分かりやすい

開始: SYN → SYN-ACK → ACK でESTABLISHED。
終了: FIN → ACK → FIN → ACK を基本形として終了します。終了が4つに分かれやすいのは、TCPが双方向通信であり、それぞれの送信方向を別々に閉じられるためです。
