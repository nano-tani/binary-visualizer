HTTPSでは、HTTPを送る前にTLSで「相手は本物か」「同じ暗号鍵を安全に作れるか」を確認します。ここではTLS 1.3の流れを学習用に簡略化して追います。

証明書は何を確認する？

ホスト名アクセス先の名前と証明書が一致するかexample.com
有効期限現在時刻が証明書の有効期間内かNot Before / After
信頼の連鎖信頼された認証局まで証明書チェーンを検証できるかRoot CA
署名証明書やハンドシェイク情報が正しく署名されているかCertificateVerify

証明書の主な役割はサーバーの身元確認です。Webページ本体を証明書の公開鍵でそのまま暗号化しているわけではありません。

暗号化すると何が変わる？

ブラウザの中HTTPリクエストGET /account HTTP/1.1
Host: example.com
ネットワーク上TLSで保護されたデータ17 03 03 8f a2 4c 91 …

TLSハンドシェイク後は、両側が導出した対称鍵でアプリケーションデータを暗号化・認証します。対称鍵は大量データを効率よく処理できます。

「鍵を送る」のではなく、同じ鍵を作る

TLS 1.3では通常、ClientHelloとServerHelloに含まれるkey shareを使って共有秘密を計算し、そこから通信に使う鍵を導出します。セッション鍵そのものを平文でネットワークへ送るわけではありません。

証明書は「このサーバーを信じてよいか」を確認し、鍵共有は「この通信だけで使う秘密」を作る役割です。似ていますが別の仕事です。

証明書エラーなら？

ホスト名不一致、期限切れ、信頼できない認証局などの問題があると、ブラウザは通常そのTLS接続を安全なHTTPSとして続行しません。

鍵マークがあることは「通信がTLSで保護され、証明書検証を通った」ことを示しますが、そのWebサイトの内容や運営者が必ず安全・善良だという意味ではありません。

HTTP / HTTPSとのつながり

DNS → TCP接続 → TLS → HTTP と考えると、前のページまでの内容が一本につながります。HTTP/3ではTCPではなくQUIC上でTLS 1.3が使われるため、実際の構成はプロトコル世代によって異なります。
